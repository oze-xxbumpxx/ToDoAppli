# 10. LLM レシピ提案（Amazon Bedrock）

> 2026-08-31 調査。**提案段階**であって確定ではない（→ [07 の D-11](./07-plan.md)）。
> 費用の懸念に answer を出すことがこのドキュメントの主目的。

## 10.1 結論

**Bedrock で実現できる。技術的な障害は無い。**
ただし **Bedrock には無料枠が無い**ので、Cognito のように「$0 で済む」とは言えない。

規模ごとの月額はこうなる（Claude Haiku 4.5、1 回あたり入力 1,000 / 出力 1,500 トークン想定）:

| 使い方 | 回数 | 月額 |
|--------|------|------|
| 開発中に手で動作確認する | 100 回/月 | **約 $0.85**（¥130 前後） |
| テストユーザー 1 人が毎日 3 回使う | 90 回/月 | 約 $0.77 |
| 仮に 1,000 回/月まで伸びた | 1,000 回/月 | 約 $8.5 |

**練習用途なら月 $1 未満**。金額そのものは問題にならない。
問題になるのは金額ではなく、**[D-10](./07-plan.md) で張った $0.01 の Budget が 2 リクエスト目で鳴る**ことと、
**予算アラートは上限ではない**という 2 点。ここは 10.3 で設計し直す。

## 10.2 なぜ Bedrock か（3 案の比較）★

Claude を呼ぶ経路は 3 つある。**どれでも同じ Messages API が使える**ので、差は課金と運用に出る。

| 案 | 課金先 | 認証情報 | この案件での評価 |
|----|--------|---------|----------------|
| **a. Amazon Bedrock** | **AWS の請求に合流** | **IAM**（鍵をアプリに持たない） | ◎ 採用案 |
| b. Claude API（第一者）を直接 | Anthropic に別途カード登録 | API キーを `.env` に置く | △ 最速だが請求と鍵が増える |
| c. Claude Platform on AWS | AWS Marketplace 経由（CCU 建て） | Marketplace 契約 | △ 機能は最新だが手続きが重い |

**案 a を推す理由は「AWS の練習になるから」ではなく、認証情報と請求の置き場所が減るから。**

- **鍵が増えない。** SDK は AWS の標準クレデンシャルチェーン（`~/.aws/credentials` → 環境変数 → ロール）を読む。
  ローカル開発では `aws configure` 済みの資格情報がそのまま使われるので、
  **`.env` に API キーを 1 本も足さずに済む**。[D-1](./07-plan.md)（トークンを localStorage に置かない）と同じ発想。
- **請求が 1 箇所に集まる。** Cognito と同じ AWS の請求に乗るので、[D-10](./07-plan.md) の Budget が
  そのまま LLM のコストも見張れる（だから 10.3 で張り直す必要がある、という話でもある）。
- **案件で説明しやすい。** 「なぜ Bedrock か」に「IAM で完結し、鍵を配らないから」と答えられる。
  「AWS を使いたかったから」より強い。

案 b が有利なのは**機能の新しさ**（10.6 の非対応リスト参照）と**着手の速さ**だけ。
そのために鍵と請求先を 1 つ増やす価値は、この規模では無い。

## 10.3 費用 ★

### 単価（2026-08-31 時点）

| モデル | 入力 | 出力 | キャッシュ読み |
|--------|------|------|--------------|
| **Claude Haiku 4.5** | $1 / 100 万トークン | $5 / 100 万トークン | $0.10 / 100 万 |
| Claude Sonnet 5 | $2 / 100 万 | $10 / 100 万 | $0.20 / 100 万 |
| Claude Opus 5 | $5 / 100 万 | $25 / 100 万 | $0.50 / 100 万 |

> Sonnet 5 の $2/$10 は「2026-08-31 までの導入価格」として案内されていたが、
> **9/1 に予定されていた $3/$15 への値上げは行われない**ことが公式に明記された。
> つまり 9/1 以降もこの単価のままでよい。

### 1 リクエストいくらか

レシピ提案 1 回を「入力 1,000 トークン（役割・出力形式・手持ちの食材）／出力 1,500 トークン（3 品分の材料と手順）」と置く:

| モデル | 入力 | 出力 | **1 回あたり** |
|--------|------|------|--------------|
| **Haiku 4.5** | $0.001 | $0.0075 | **$0.0085**（約 1.3 円） |
| Sonnet 5 | $0.002 | $0.015 | $0.017（約 2.6 円） |
| Opus 5 | $0.005 | $0.0375 | $0.0425（約 6.4 円） |

**支配的なのは出力側**（Haiku で 88%）。安くしたければモデルを落とすより**出力を短くする**方が効く。

### プロンプトキャッシュはこの規模では効かない ★

システムプロンプトを使い回せば入力が 1/10 になる——のだが、
**キャッシュには最小プレフィックス長（512〜4,096 トークン、モデル依存）がある**。
レシピ提案のシステムプロンプトは 500 トークン程度なので**下限に届かず、黙ってキャッシュされない**。

効かない最適化を入れて「効いているつもり」になるのが一番まずいので、
**最初はキャッシュを入れない**。入れるなら `usage.cache_read_input_tokens` が 0 でないことを必ず確認する。

### 無料枠は無い

Cognito と決定的に違う点。**Bedrock のオンデマンド呼び出しに無料枠は無い**ので、
1 リクエスト目から課金される。「無料のはずなのに請求が出た」という [D-10](./07-plan.md) の前提が、
この機能に限っては**成り立たない**。

> 出典の制約: この環境からは `aws.amazon.com` に到達できず、AWS の料金ページを直接確認できていない。
> 上の単価は Anthropic 公式の第一者料金であり、Bedrock のオンデマンド単価はこれにほぼ一致する
> （エンドポイント種別による差は下記）。**請求の正本は AWS の料金ページ**なので、
> 有効化前に一度自分の目で突き合わせること。

### グローバル / リージョナルの 10% 差

Bedrock には 2 種類のエンドポイントがある。

| 種別 | 経路 | 価格 |
|------|------|------|
| **グローバル**（既定） | 空きのあるリージョンへ動的にルーティング | 割増なし |
| リージョナル（`jp.` / `us.` など） | 指定した地理に固定。データ所在要件向け | **+10%** |

**この案件はグローバルでよい。** データ所在の要件が無いのに 10% 払う理由が無い。
なお東京リージョン（`ap-northeast-1`）はグローバル・JP・単一リージョンのすべてに対応しているので、
後から「国内に固定したい」と言われても**モデル ID の接頭辞を変えるだけ**で移れる。

### ★ D-10 の $0.01 Budget が 2 リクエスト目で鳴る

これが今回いちばん効く発見。

Haiku で 1 回 $0.0085 なので、**2 回叩けば $0.017 で閾値 $0.01 を超える**。
[D-10](./07-plan.md) の guardrail は「無料のはずなのに請求が出たら即座に知る」ための仕掛けなので、
**課金が正常な機能を同じ口で見張ると、鳴りっぱなしになって意味を失う**。
`FORECASTED` を避けた 6.2 の議論と同じ失敗を、閾値の側でやることになる。

対応は 2 案。

| 案 | 内容 | 失うもの |
|----|------|---------|
| **A（推奨）** | guardrail は $0.01 のまま**コストフィルタで「無料であるべきサービス」に限定**し、Bedrock 用の 2 本目を別に張る | なし。ただし Budget の無料枠は **2 個/アカウント**なのでこれで使い切る |
| B | guardrail の閾値を Bedrock 込みの現実的な額（$3 など）に引き上げる | **「$0 のはず」という canary の性質**。異常検知の感度が落ちる |

**案 A を推す。** guardrail の価値は金額ではなく「0 であるべきものが 0 か」を見ていることにあり、
そこを手放すと [D-10](./07-plan.md) を決めた意味がなくなる。

> 未検証: `aws_budgets_budget` の `cost_filter` でサービス単位の絞り込みがどう書けるか、
> 除外指定が可能かは AWS のドキュメントに到達できず確認できていない。
> **包含指定（見張りたいサービスを列挙する）なら確実に書ける**ので、そちらで組む前提にしておく。

### ★ 予算アラートは上限ではない。上限はアプリ側に置く

[6.2](./06-infra-ci.md) に既に書いてある通り、**AWS の請求データ更新は 1 日数回**で、
課金からアラートまで数時間〜1 日遅れる。つまり Budget は**事後通知**であって、
暴走したループを止める仕掛けではない。**上限はアプリ側に持たせる。**

この案件の原則（[7.3](./07-plan.md)）——**「チェックを書く」のではなく「通れない構造にする」**——を、
そのままコストに適用する:

| 仕掛け | 何を保証するか |
|--------|--------------|
| **`max_tokens` を必ず指定する** | 1 リクエストの**最大**コストが計算可能な定数になる |
| **モデル ID を union 型で持つ** | 設定ミスで Opus が選ばれる経路が**型で消える**（`string` にしない） |
| **1 ユーザー 1 日あたりの提案回数上限** | 月額の理論上限が決まる。Domain Service で表現する（→ 10.5） |

これで金額を**設計値として言い切れる**ようになる:

```
1 回の上限 = 入力 1,000 × $1/1M + max_tokens 2,000 × $5/1M = $0.011
月額の理論上限 = $0.011 × 5 回/日 × 30 日 × ユーザー数
              = $1.65 / 月 / ユーザー
```

「だいたい安いです」ではなく「**1 ユーザーあたり月 $1.65 を超えられない構造です**」と説明できる。
これが案件で問われる「なぜそう作ったか」に対する答えになる。

## 10.4 モデル選定

**Claude Haiku 4.5（`anthropic.claude-haiku-4-5`）で始める。**

| 観点 | 判断 |
|------|------|
| 品質 | レシピ提案は**創造性より形式順守**が要る仕事。Haiku で足りる。足りなければ Sonnet 5 に上げればよく、**変わるのは文字列 1 つ** |
| 費用 | Sonnet 5 の 1/2、Opus 5 の 1/5 |
| 待ち時間 | 出力 1,500 トークンを数秒で返す。画面が固まらない |
| 利用開始 | **全 Bedrock 利用者に開放済み**。モデルアクセス申請の待ちが発生しない（Opus 5 は個別の条件あり） |

**上げるとしたら Sonnet 5。** 「品質が足りない」と感じたときに初めて上げる。
最初から Opus 5 を選ぶ理由はこの用途には無い。

## 10.5 置き場所 ★

**既存の層構成にそのまま乗る。新しい考え方は 1 つも要らない。**

```
apps/api/src/recipes/
  recipes.module.ts
  presentation/
    recipes.controller.ts
    dto/suggest-recipes.dto.ts
    dto/recipe-suggestion-response.dto.ts
  application/
    suggest-recipes.usecase.ts
    suggest-recipes.usecase.spec.ts       ← ここが無料になる（後述）
  domain/
    recipe.entity.ts
    recipe-suggester.ts                   ← interface（ポート）+ Symbol
    recipe.errors.ts
    services/
      daily-suggestion-quota.ts           ← 1 日の回数上限（Domain Service）
  infrastructure/
    bedrock-recipe-suggester.ts           ← 実装（アダプタ）。SDK を import する唯一の場所
  testing/
    stub-recipe-suggester.ts              ← 固定レスポンスを返す
```

`TodoRepository` / `PrismaTodoRepository` と**同じ形**:

```ts
// domain/recipe-suggester.ts
export interface RecipeSuggester {
  suggest(request: SuggestionRequest): Promise<readonly Recipe[]>;
}

/** interface は実行時に存在しないので Symbol で注入する（docs/04-backend.md 4.4）。 */
export const RECIPE_SUGGESTER = Symbol('RecipeSuggester');
```

### ★ 依存性逆転がそのまま「テストが無料」に化ける

[4.3](./04-backend.md) で「UseCase が Prisma を知らないのでテストで差し替えられる」と書いた利点が、
LLM では**そのまま金額として返ってくる**。

`SuggestRecipesUseCase` が `RECIPE_SUGGESTER` にしか依存しないので、
単体テストは `StubRecipeSuggester` を挿すだけで済み、**CI が何回回っても課金は $0**。

これは副産物ではなく、**Bedrock を採用してよい根拠そのもの**。
UseCase が AWS SDK を直接 `new` する設計だったら、
「テストのたびに課金される」か「テストを書かない」の二択になっていた。

> `DailySuggestionQuota` を Domain Service にするのは F-09（`TodoTitleUniquenessChecker`）と同じ理由。
> 「自分以外の履歴を見ないと判定できない」ので Entity には置けない。
> [D-8](./07-plan.md) で足した練習対象が、**追加要件なしでもう 1 回使える**。

## 10.6 呼び出し口と、Bedrock で使えない機能 ★

### 新旧 2 つの入口がある。新しい方を使う

| 入口 | 形 | 使うか |
|------|----|-------|
| **Claude in Amazon Bedrock**（新） | `https://bedrock-mantle.{region}.api.aws/anthropic/v1/messages`。**第一者 API と同じリクエスト形**。SSE ストリーミング | **こちら** |
| Claude on Amazon Bedrock（旧） | `InvokeModel` / `Converse`、ARN 付きモデル ID、AWS 独自のイベントストリーム | 使わない |

TypeScript の場合:

```bash
pnpm --filter @todoapli/api add @anthropic-ai/bedrock-sdk
```

```ts
// infrastructure/bedrock-recipe-suggester.ts
import { AnthropicBedrockMantle } from '@anthropic-ai/bedrock-sdk';

// 資格情報とリージョンは AWS の標準チェーン（環境変数 → ~/.aws → ロール）から解決される。
// .env に鍵を置かない、が成立するのはこのため。
const client = new AnthropicBedrockMantle({ awsRegion: 'ap-northeast-1' });

const message = await client.messages.create({
  model: 'anthropic.claude-haiku-4-5',
  max_tokens: 2000,              // ★ 1 回あたりの上限を物理的に固定する（10.3）
  system: SYSTEM_PROMPT,
  messages: [{ role: 'user', content: userPrompt }],
});
```

IAM 側に要るのは、対象モデルの ARN に絞った **`bedrock-mantle:CreateInference`**。
サービスロール（推奨）／IAM ロールの引き受け／ベアラートークンの 3 経路があるが、
**ローカル開発なら `aws configure` 済みのユーザーに直接ポリシーを付ける**のが最短。

### 設計に効く非対応機能 ★

Bedrock では第一者 API の一部が使えない。**このうち 1 つがレシピ提案の設計に直撃する。**

| 機能 | Bedrock | 影響 |
|------|---------|------|
| **Structured Outputs** | **非対応** | ★ **JSON を型で保証できない**。下記の対応が要る |
| Files API / URL 入力 | 非対応 | 影響なし（画像を送らない） |
| サーバ側ツール（Web 検索など） | 非対応 | 影響なし |
| Message Batches | 非対応 | 影響なし（対話的に使う） |
| プロンプトキャッシュ | 対応 | ただし 10.3 の通りこの規模では効かない |

**Structured Outputs が使えない**ので、「必ずこの JSON スキーマで返る」をプラットフォームに保証させられない。
レシピ提案は構造化された出力（品名・材料・手順）が欲しい機能なので、ここは自分で埋める:

1. **Tool Use で受け取る。** ツール定義のスキーマに沿った入力として返させる。実質これが構造化出力の代替になる
2. **戻り値を必ず検証する。** `class-validator` は既に入っている。**LLM の出力は外部入力**として扱い、
   DTO と同じ厳しさで検証する（[2.3](./02-domain-and-api.md) の「サーバ側バリデーションは目的が違う」がそのまま当てはまる）
3. **検証に落ちたら失敗として扱う。** 握り潰して壊れた JSON を画面に流さない

**「LLM の出力を信用しない」は妥協ではなく設計。** 境界の外から来た値は全部検証する、という既存方針と一貫している。

## 10.7 表面（API と画面）

### エンドポイント

```
POST /api/v1/recipe-suggestions
```

**Todo のサブリソース（`/todos/:id/...`）にしない。** レシピ提案は特定の Todo に属する概念ではなく、
「手持ちの食材から献立を出す」独立したユースケース。
`todos/` の下に置くと `TodosModule` が LLM を知ることになり、[4.2](./04-backend.md) の機能単位の切り方が崩れる。

認可は既存の Guard がそのまま効く。`ownerId` は `@CurrentUser()` から取る——
[2.4](./02-domain-and-api.md) の「Repository が ownerId を必須で受け取る」と同じく、
`DailySuggestionQuota` も `ownerId` を必須引数にすることで、**他人の枠を消費する経路を型で消す**。

### 画面側

**`useFetcher` を使う。`Form` ではない。**

[3.2](./03-frontend.md) の使い分け——**遷移するか、しないか**——に照らすと、
レシピ提案は「いまの画面に結果を差し込む」操作なので `useFetcher`。
完了トグル（F-06）と同じ側に立つ。

ただし完了トグルと違って**楽観的更新はできない**。結果を予測できないので、
`fetcher.state` を見てローディングを出し、返ってきてから描く。
**待ち時間が数秒ある**のがこの機能の UX 上の特徴で、
「押した瞬間に何か出る」他の操作とは体感が違う。ここは割り切る。

ストリーミング（1 文字ずつ出す）は React Router の `loader`/`action` の外に出る話になり、
**練習対象が 1 つ増える**わりに設計上の学びが薄い。**やらない。**

## 10.8 Terraform と CI

| 対象 | Terraform で書くか |
|------|------------------|
| Bedrock 呼び出し用の IAM ポリシー / ロール | **書く**。モデル ARN に絞った `bedrock-mantle:CreateInference` |
| Bedrock 用の 2 本目の Budget | **書く**（10.3 の案 A） |
| guardrail Budget へのコストフィルタ追加 | **書く**（既存 `budget.tf` の修正） |
| モデルアクセスの有効化 | **要確認**。コンソール操作が必要な可能性がある。provider のバージョンで調べてから決める |
| CloudWatch / CloudTrail への呼び出しログ | 任意。30 日ローリングでの保持が推奨されている |

CI は変えなくてよい。**単体テストがスタブで回る**（10.5）ので、
GitHub Actions に AWS の資格情報を持ち込む必要が無い。
[6.3](./06-infra-ci.md) で `terraform plan` を CI に入れないと決めた理由と同じ線が引ける。

## 10.10 決定案 D-11

**案 a：Bedrock（Claude in Amazon Bedrock）で実装する。モデルは Haiku 4.5、グローバルエンドポイント。**
併せて **D-10 の guardrail を案 A の形（フィルタ + 2 本目）に張り直す。**

判断の骨子は 3 つ:

1. **費用は月 $1 未満で、しかも「上限がいくらか」を構造で言い切れる**（10.3）
2. **既存の層構成に新しい概念を 1 つも足さずに乗る**。ポートとアダプタ、Domain Service、
   スタブでの単体テスト——[D-2](./07-plan.md)・[D-8](./07-plan.md) で既に決めたものの再利用だけで組める（10.5）
3. **鍵が 1 本も増えない。** IAM で完結する（10.2）

**引き受けるコストは「$0 ではなくなること」そのものではなく、
[D-10](./07-plan.md) の guardrail を設計し直す手間**。それは 10.3 で片付く。
