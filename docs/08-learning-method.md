# 08. 学習方法の設計（模写をどう組み込むか）

## 8.1 模写の失敗モードと対策

写経は強力だが、放っておくと必ず次のどれかに落ちる。

| 失敗モード | 症状 | 対策 |
|-----------|------|------|
| コピペに堕す | 手を動かした気になるが何も残らない | **手本を貼らない。** 別ファイルを見ながら手で打つ |
| 写せたが説明できない | 動くコードはあるが、なぜそう書くか言えない | 模写の直後に**横展開**（後述）を必ずやる |
| 手本が完成品すぎる | 途中の試行錯誤が見えず、白紙からは書けないまま | 手本に**意図的な空欄**を残す |

> 模写は「書き方を手に馴染ませる」ためのもので、
> 「理解した証明」にはならない。**証明は横展開でしか取れない。**

## 8.2 三分割：何を模写し、何を自力で書くか ★

| 種類 | 例 | 担当 |
|------|-----|------|
| **配線・設定** | tsconfig / ESLint / Vite 設定 / compose.yaml / CI の yaml | **Claude が作る**（模写しない） |
| **定型コード** | NestJS の層構成・DI トークン・デコレータの並び、`routes.ts`、Terraform の HCL | **Claude が手本 → 模写** |
| **判断が要る部分** | 業務ロジック、`Form` と `useFetcher` の選択、テストケース設計 | **自力で書く** |

### 配線・設定を模写しない理由

`tsconfig.json` を手で写しても学びがほぼない。設定は「調べて貼る」のが実務でも正しく、
覚える対象ではない。ここは 2026-08-21 に決めた「骨組みは Claude」の合意そのまま。

### 定型コードを模写する理由

NestJS の層構成や DI トークンの書き方は、**知らなければ白紙からは絶対に書けない**。
かつ一度書ければ以降ずっと同じ形。ここは模写の投資対効果が最も高い。
React Router の `loader` の型付けも同じ（API の形を知らないと書きようがない）。

### 判断が要る部分を自力で書く理由

`Form` と `useFetcher` の使い分け（[03 の 3.2](./03-frontend.md)）は、
**判断そのものが学習対象**。写したら学習内容が消える。
テストケースの設計も同様で、「何をテストすべきか」がテストの本体。

## 8.3 サイクル：縦に 1 本 → 横展開

各フェーズで、**全層を貫く 1 機能だけ**を手本にする。

```
    Controller    UseCase    Repository    Prisma
        │            │           │           │
 一覧  ━┿━━━━━━━━━━━━┿━━━━━━━━━━━┿━━━━━━━━━━━┿━  ← 手本（模写する）
        │            │           │           │
 作成   ┆            ┆           ┆           ┆   ← 自力（同じ形で書く）
 取得   ┆            ┆           ┆           ┆   ← 自力
 更新   ┆            ┆           ┆           ┆   ← 自力
 削除   ┆            ┆           ┆           ┆   ← 自力
```

### なぜ「一覧取得」を手本にするのか

- Controller → UseCase → Repository → Prisma の**全層を通る**
- 認可（`ownerId` の受け渡し、[02 の 2.4](./02-domain-and-api.md)）も通る
- フロントは `loader` → 表示という**最小経路**
- **副作用がない**ので、失敗しても何も壊れない

### 横展開が理解度テストになる

一覧を模写したあと、作成・取得・更新・削除は「同じ形」で書ける。
書けなければ、模写が理解になっていないという判定がその場で出る。

しかも横展開先には設計上の山が含まれている:

| 横展開先 | 越える山 |
|---------|---------|
| 作成 | `Form` + `action`（遷移する送信） |
| 更新 | `useFetcher` + 楽観的更新（遷移しない送信） |
| 削除 | 送信後のリダイレクト先の判断 |

**`Form` と `useFetcher` の使い分けを、手本なしで自分で選ぶことになる。**
これは 8.2 の「判断は自力」と一致している。

## 8.4 各フェーズの手本と横展開

| Phase | 手本（模写） | 横展開（自力） |
|-------|------------|--------------|
| 1 | Todo 一覧の API（4 層すべて） | 作成 / 取得 / 更新 / 削除 の API |
| 2 | `/app/todos` の loader と一覧表示 | 詳細・作成・削除・完了トグル |
| 3 | CI の yaml | （模写不要。Claude が作る） |
| 4 | Cognito の Terraform | JWKS 検証 Guard への差し替え |
| 5 | — | Passkey 有効化（手本なし。ここは一緒に調べる） |

Phase 5 に手本がないのは、**私も正解を知らないから**。
Cognito の Passkey 設定は仕様の変化が速く、
最新のドキュメントを見ながら進めることになる。

## 8.5 進め方のルール

1. 手本は `reference/` に置く。**`apps/` には自分で打つ**
2. 打ち終わったら、**手本を閉じて**横展開に入る
3. 詰まったら手本を見てよい。ただし**見たことを記録する**（そこが弱点）
4. 横展開が終わったら、Claude がレビューする

### レビューで見るもの

「動くか」ではなく「**設計通りか**」を見る。

- `ownerId` を Repository に渡しているか（[02 の 2.4](./02-domain-and-api.md)）
- Controller に業務ロジックが漏れていないか（[04 の 4.2](./04-backend.md)）
- 遷移しない送信に `Form` を使っていないか（[03 の 3.2](./03-frontend.md)）
- UseCase が Prisma を import していないか（[04 の 4.3](./04-backend.md)）

## 8.6 要決定（→ [07-plan.md](./07-plan.md) の 7.2 に追加）

| # | 決定事項 | 選択肢 | 推奨 |
|---|---------|-------|------|
| D-6 | 手本の範囲 | 全フェーズで縦 1 本ずつ / Phase 1 だけ / 全機能 | **全フェーズで縦 1 本ずつ** |
| D-7 | 手本の置き方 | `reference/` に完成品 / 空欄（TODO）付き / 公式サンプルを使う | **`reference/` に完成品** |

### D-7 で公式サンプルを使わない理由

React Router や NestJS の公式サンプルは、この `docs/` の設計とは
**別の設計方針で書かれている**（層を分けていない、認可の考え方が違う 等）。
設計を決めた直後に別設計のコードを写すと、どちらが自分の方針か分からなくなる。
手本は**この設計に沿ったもの**であるべき。
