## 5.2 設計判断：WebAuthn を自前実装しない ★

Cognito には `USER_AUTH` フローで `WEB_AUTHN` チャレンジを自前 UI で扱う道もあるが、
**Managed Login（Hosted UI）に任せる**。

理由:
- `navigator.credentials.create()` / `.get()` の attestation / assertion 処理は仕様が細かく、
  バグると「なぜか特定の端末だけログインできない」という最悪の形で表面化する
- 案件で求められるのは「**Passkey が使える構成を組めること**」であって、
  WebAuthn プロトコルの再実装ではない
- Managed Login はブラウザ差異・エラー文言・リカバリ導線を面倒見てくれる

**トレードオフ**：ログイン画面のデザイン自由度が Managed Login の
ブランディング設定の範囲に制限される。今回は許容する。

## 5.3 設計判断：トークンをどこに保管するか ★要決定

| 案 | 内容 | XSS 耐性 | 実装コスト |
|----|------|---------|-----------|
| A | localStorage に保存 | ✗ スクリプトから読める | 低 |
| B | **メモリ（変数）のみ**、リロード時は Cognito セッションで再取得 | △ 盗まれにくいがタブ再読込で消える | 中 |
| C | BFF を立てて httpOnly + SameSite Cookie | ◎ | 高（2〜3 日） |

**推奨：B**

- A は案件レビューで確実に指摘される。「動くから」で選んではいけない
- C が本来の正解だが、BFF の実装で日程を食い潰す
- B にした上で「本番なら C にすべき、理由は〜」と**説明できる状態**を作るのが
  今回の目的に合う

> これはあなたの判断が要る点です。→ `07-plan.md` の要決定一覧を参照。

## 5.4 JwtAuthGuard の設計

Cognito の JWKS（公開鍵）で署名を検証する。検証項目:

| 項目 | 検証内容 |
|------|---------|
| 署名 | JWKS の公開鍵で検証 |
| `iss` | `https://cognito-idp.<region>.amazonaws.com/<userPoolId>` と一致 |
| `exp` | 期限切れでない |
| `token_use` | **`"access"` であること** |
| `client_id` | 自分のアプリクライアント ID と一致 |

### `token_use` を検証する理由

Cognito は ID トークンとアクセストークンの両方を発行する。
**ID トークンは「誰か」を伝えるもの、アクセストークンは「何をしてよいか」を伝えるもの。**
API の認可に ID トークンを受け付けてしまうのはよくある事故なので、明示的に弾く。

### JWKS はキャッシュする

毎リクエストで JWKS を取りに行くと、Cognito への往復がボトルネックになり、
かつ AWS 側のレート制限に当たる。鍵は滅多にローテートされないのでキャッシュする。

検証後、`req.user = { sub, email }` を詰め、`@CurrentUser()` デコレータで取り出す。
この `sub` がそのまま `ownerId` になる（設計判断 2.1）。

## 5.5 Phase 分割 ★日程管理の要

AWS を触らずにアプリ本体を完成させられるようにする。

| Phase | 認証の中身 | AWS 必要か |
|-------|-----------|-----------|
| **A** | 自前発行のダミー JWT（HS256）。発行スクリプトを 1 本書く | 不要 |
| **B** | Cognito を Terraform で作成、Managed Login でパスワードログイン | 必要 |
| **C** | Cognito の Passkey / WebAuthn を有効化 | 必要 |

**勘所：Phase A と B/C の差分を「署名検証ロジックだけ」に閉じ込める。**

Guard の形（どこで呼ばれ、何を `req.user` に詰めるか）は 3 フェーズとも同じ。
変わるのは「HS256 の共有鍵で検証」か「JWKS の公開鍵で検証」かだけ。
ここを最初から分離しておけば、Phase B への移行が 1 ファイルの差し替えで済む。

Phase A のうちにフロント・バックの全機能（F-03〜F-07）を完成させられるので、
**AWS アカウントの準備が遅れても開発が止まらない。**

## 5.6 実装時に確認が必要な点

- Cognito の Passkey は **Essentials tier 以上**が必要（Lite では有効化不可）。
  ティア構成と価格は変わりうるので、着手時に AWS の公式ドキュメントで最新を確認すること
- Managed Login は**新しいブランディング版**でないと WebAuthn に対応しない。
  Terraform のリソース名・属性名は実装時にプロバイダのドキュメントで確認する
- **WebAuthn の Relying Party ID はドメインに紐づく。**
  `localhost` で登録した Passkey は本番ドメインには引き継がれない（WebAuthn の仕様であり、不具合ではない）
