# 05. 認証設計（Cognito + Passkey）

## 5.1 完成形のフロー

```
[ブラウザ]                [Cognito Managed Login]          [NestJS API]
    │                              │                             │
    │ 1. /login で「ログイン」押下 │                             │
    ├─────────────────────────────>│                             │
    │    Authorization Code + PKCE  │                             │
    │                              │                             │
    │ 2. Passkey 認証               │                             │
    │ <──── WebAuthn チャレンジ ────┤                             │
    │ ────> 生体認証で署名 ────────>│                             │
    │                              │                             │
    │ 3. code を付けてリダイレクト  │                             │
    │<─────────────────────────────┤                             │
    │    /auth/callback?code=...    │                             │
    │                              │                             │
    │ 4. code + code_verifier で交換│                             │
    ├─────────────────────────────>│                             │
    │<── ID / Access / Refresh ─────┤                             │
    │                              │                             │
    │ 5. Authorization: Bearer <access_token>                     │
    ├────────────────────────────────────────────────────────────>│
    │                              │  6. JWKS を取得して署名検証  │
    │                              │<────────────────────────────┤
    │<──────────────── 200 + データ ──────────────────────────────┤
```

## 5.2 設計判断：WebAuthn を自前実装しない ★

Cognito には `USER_AUTH` フローで `WEB_AUTHN` チャレンジを自前 UI で扱う道もあるが、
**Managed Login（Hosted UI）に任せる**。

理由:
- `navigator.credentials.create()` / `.get()` の attestation / assertion 処理は仕様が細かく、
  バグると「なぜか特定の端末だけログインできない」という最悪の形で表面化する
- 案件で求められるのは「**Passkey が使える構成を組めること**」であって、
  WebAuthn プロトコルの再実装ではない
- Managed Login はブラウザ差異・エラー文言・リカバリ導線を面倒見てくれる

**トレードオフ**：ログイン画面のデザイン自由度が Managed Login の
ブランディング設定の範囲に制限される。今回は許容する。

## 5.3 設計判断：トークンをどこに保管するか ★要決定

| 案 | 内容 | XSS 耐性 | 実装コスト |
|----|------|---------|-----------|
| A | localStorage に保存 | ✗ スクリプトから読める | 低 |
| B | **メモリ（変数）のみ**、リロード時は Cognito セッションで再取得 | △ 盗まれにくいがタブ再読込で消える | 中 |
| C | BFF を立てて httpOnly + SameSite Cookie | ◎ | 高（2〜3 日） |

**推奨：B**

- A は案件レビューで確実に指摘される。「動くから」で選んではいけない
- C が本来の正解だが、BFF の実装で日程を食い潰す
- B にした上で「本番なら C にすべき、理由は〜」と**説明できる状態**を作るのが
  今回の目的に合う

> これはあなたの判断が要る点です。→ `07-plan.md` の要決定一覧を参照。

## 5.4 JwtAuthGuard の設計

Cognito の JWKS（公開鍵）で署名を検証する。検証項目:

| 項目 | 検証内容 |
|------|---------|
| 署名 | JWKS の公開鍵で検証 |
| `iss` | `https://cognito-idp.<region>.amazonaws.com/<userPoolId>` と一致 |
| `exp` | 期限切れでない |
| `token_use` | **`"access"` であること** |
| `client_id` | 自分のアプリクライアント ID と一致 |

### `token_use` を検証する理由

Cognito は ID トークンとアクセストークンの両方を発行する。
**ID トークンは「誰か」を伝えるもの、アクセストークンは「何をしてよいか」を伝えるもの。**
API の認可に ID トークンを受け付けてしまうのはよくある事故なので、明示的に弾く。

### JWKS はキャッシュする

毎リクエストで JWKS を取りに行くと、Cognito への往復がボトルネックになり、
かつ AWS 側のレート制限に当たる。鍵は滅多にローテートされないのでキャッシュする。

検証後、`req.user = { sub, email }` を詰め、`@CurrentUser()` デコレータで取り出す。
この `sub` がそのまま `ownerId` になる（設計判断 2.1）。

## 5.5 Phase 分割 ★日程管理の要

AWS を触らずにアプリ本体を完成させられるようにする。

| Phase | 認証の中身 | AWS 必要か |
|-------|-----------|-----------|
| **A** | 自前発行のダミー JWT（HS256）。発行スクリプトを 1 本書く | 不要 |
| **B** | Cognito を Terraform で作成、Managed Login でパスワードログイン | 必要 |
| **C** | Cognito の Passkey / WebAuthn を有効化 | 必要 |

**勘所：Phase A と B/C の差分を「署名検証ロジックだけ」に閉じ込める。**

Guard の形（どこで呼ばれ、何を `req.user` に詰めるか）は 3 フェーズとも同じ。
変わるのは「HS256 の共有鍵で検証」か「JWKS の公開鍵で検証」かだけ。
ここを最初から分離しておけば、Phase B への移行が 1 ファイルの差し替えで済む。

Phase A のうちにフロント・バックの全機能（F-03〜F-07）を完成させられるので、
**AWS アカウントの準備が遅れても開発が止まらない。**

## 5.6 実装時に確認が必要な点（2026-08-29 に確認済み）

- Cognito の Passkey は **Essentials tier 以上**が必要（Lite では有効化不可）→ 確認済み。ESSENTIALS で作成
- Managed Login は**新しいブランディング版**でないと WebAuthn に対応しない
  → `managed_login_version = 2` で作成済み
- アプリクライアントに `ALLOW_USER_AUTH`（選択式認証）が要る → 設定済み

### 訂正：`localhost` の Passkey は本番に引き継げない、は**この構成には当てはまらない** ★

> 初版に「`localhost` で登録した Passkey は本番ドメインには引き継がれない」と書いたが、
> **Managed Login に任せる構成（5.2 の決定）では誤り**だった。

WebAuthn の鍵は Relying Party ID（ドメイン）に紐づく。ここまでは正しい。
誤っていたのは「そのドメインがアプリのドメインである」という前提で、
**WebAuthn の儀式が動くのは Managed Login のページ、つまり Cognito のドメイン**である。

```
アプリ          http://localhost:5173        ← 儀式に関与しない
Managed Login   https://<prefix>.auth.<region>.amazoncognito.com   ← ここが RP
```

したがって:

- アプリを `localhost` から本番ドメインに移しても、**Passkey は失効しない**
- 逆に、Cognito 側に**カスタムドメインを付けると RP ID が変わる**ため、
  それ以前に登録された Passkey は使えなくなる（AWS の仕様上、カスタムドメインがある場合は
  RP ID をそのドメインにすることが必須）
- 5.2 で WebAuthn を自前実装しないと決めた副次的な効果として、
  **開発と本番でドメインが変わる問題が消えている**

出典: [WebAuthnConfigurationType](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_WebAuthnConfigurationType.html)（2026-08-29 確認）

## 5.7 Passkey の設定（Phase 5 の決定）

| # | 決定 | 内容 | 理由 |
|---|------|------|------|
| D-11 | RP ID | `<prefix>.auth.<region>.amazoncognito.com` | 儀式が動くオリジンと一致させる必要がある（5.6） |
| D-12 | `user_verification` | **`required`** | Passkey を**第 1 要素**として使う。「持っているだけ」で通ると弱い |
| D-13 | パスワードを残すか | **残す**（`["PASSWORD", "WEB_AUTHN"]`） | 端末紛失・登録失敗時の復旧経路。最初の 1 個を登録するにもログインが要る |

### D-12 の補足

`preferred` にすると、ユーザー検証（生体認証・PIN）に対応しない古いセキュリティキーでも
登録できてしまう。Passkey が MFA の 2 要素目なら `preferred` でも成立するが、
この設計では**パスワードの代わり**なので、認証器側で本人確認まで済ませる必要がある。

### D-13 が「パスワードレス」と矛盾しない理由

「パスワードレスにする」ことと「パスワードを消す」ことは別物である。
利用者が日常的にパスワードを入力しない状態を作るのが目的であって、
復旧手段まで消すと、端末を失った時点でアカウントに二度と入れなくなる。

なお、Terraform プロバイダ（aws v6.62）は `FactorConfiguration` を公開していないため、
Passkey は既定の **`SINGLE_FACTOR`**（＝第 1 要素）として扱われる。
これは今回の意図と一致しているので、そのままでよい。

## 5.8 見落としていた前提：Passkey は「有効にすれば使える」ではない ★

Phase 5 は「インフラ設定だけで終わる」と見積もっていたが、**外れた**。
実装中に判明した AWS の仕様が 2 つある（2026-08-29 確認）。

| 仕様 | 帰結 |
|------|------|
| 登録を促されるのは**サインアップ直後だけ** | Passkey を後から有効化しても、**既存ユーザーには何も起きない** |
| ログイン画面が Passkey を出すのは**登録済みユーザーだけ** | 0 個の状態では選択肢に現れず、利用者は登録手段に辿り着けない |

つまり「有効化した後に既存ユーザーが登録する経路」は、**アプリ側が用意しなければ存在しない**。

### 対応：Managed Login の登録ページへ明示的に送る

```
https://<domain>/passkeys/add?client_id=<clientId>&redirect_uri=<登録済みのコールバック>
```

`apps/web` のヘッダーに「Passkey を登録」を置き、このページへ素の遷移をする。
セッションが無い場合は `?result=invalid_session` を付けて跳ね返されるので、
コールバック側で `code` の有無と `result` の有無を分けて扱う必要がある。

### D-1（トークンはメモリのみ）との相互作用

Cognito のドメインへ素の遷移をすると SPA が破棄され、**アクセストークンが失われる**。
そのため登録後はログイン画面に戻る。ただし Cognito 側のセッションは生きているので、
ボタンを 1 回押すだけで実質素通りで戻ってくる。
D-1 のトレードオフが利用者から見える形で出る、数少ない場面のひとつ。

### 案件で使える教訓

**「機能を有効にする」と「利用者がその機能に到達できる」は別物。**
既存ユーザーへの移行経路は、機能追加の設計に必ず含める。
今回は Phase 5 の見積もりが「3 行」から「3 行 + フロントの導線 + コールバックの分岐」に増えた。
